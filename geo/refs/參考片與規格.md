# 地理系統短影音：開始之前要知道的

**這一份寫給另一個 Claude**，你要在一個空的專案裡從零做「以地理系統為中心的
短影音」。不共用任何既有程式。

寫這一份的人在另一個短影音專案待了很久。**底下只寫「短影音這個形式本身」
的知識**，和參考片拆出來的東西 —— 那邊的架構和那邊的錯都留在那邊，
跟你要做的事無關。

搭配讀：`四處觀察_紐約地圖短影音_0.2秒分鏡與特效拆解.md`。
那是對一支 72 秒地理短影音的逐格拆解，是你目前最接近規格書的東西。

---

## 一、先看清楚參考片在做什麼

那份拆解表有 356 個取樣點。算出來：

```
72 秒、約 130 次畫面切換、平均 0.55 秒換一次
```

這個節奏是這種片子的特徵。但**它不是做了 130 個鏡頭**。

整支片只用 **14 個代碼**（C、A、D、W、S、Q、M、P、T、N、I、J、K、R），
每一個是「同一份地圖工程 ＋ 不同的中心點和縮放 ＋ 不同的圖層開關」。
N 出現三十幾次、S 二十幾次、C 二十次。

**所以整支片的成本結構是這樣：**

```
做 14 個可重複使用的地圖預設     一次性的工
照旁白的語義一直回切             接近零成本
```

這是整份拆解文件最重要的一句話：**素材是參數，不是檔案。**

一個預設是一組數字（中心經緯度、縮放級別、哪幾個多邊形圖層、每一面的填色
和透明度、要不要畫縣界、標哪幾個地名）。回切一次只是換一組數字，不是再去
找一張圖、再輸出一次。你的第一個設計決定應該是把「預設」做成可以宣告的
東西 —— 一個 JSON 一個預設。

### 那份文件自己點出的兩個反直覺結論

**一、大量畫面是硬切回到既有地圖，不是連續的飛行。** 原文：「避免把所有
跳切誤做成 zoom」。看那支片最直覺的印象（一路飛過去）是錯的。這件事直接
決定你的工程量 —— 做連續飛行要算相機軌跡，做硬切只要存預設。

**二、那支片是 72 秒不是 60 秒。** 文件最後一條寫著：要壓到 60 秒得重寫
旁白和刪鏡頭，**不能靠加快所有動作**。

## 二、短影音這個形式，時間是怎麼長出來的

這一節是做任何一支口播短影音都會遇到的，跟地理無關。

### 長度是寫稿的時候決定的，不是壓片的時候救的

「太長了就加速」永遠只能救幾個百分點。60 秒的片子超出 10 秒，加速會讓
整支片聽起來是趕的，而畫面也跟著快。真正的變數是**寫幾個字**。

所以流程的順序應該是：先確定一句話有幾秒 → 算出那幾秒唸得完幾個字 →
叫模型照那個字數寫。反過來做（先寫再看多長）會一直重寫。

### 「幾秒唸得完幾個字」要量，不要換算

同一個合成器、同一個聲音、同一種語速，唸一段真的稿子，**去掉靜音之後**
量。不要從別的語言換算，也不要用別人的數字。

而且要分清楚在數什麼：字元、字母、單字是三種不同的數法。中文一個字同時是
一個字、一個字元、一個 word，所以這件事在中文看不出來；地理題材如果有
中英對照的地名，你會碰到。

### 停頓吃掉的時間比你以為的多

一支 60 秒的片，光是句號換氣和刻意的停頓就可能吃掉十幾秒。算字數額度的
時候要先扣掉它，而**它跟稿子長度成比例，不是一個常數** —— 句子多、逗號多，
停頓就多。

### 秒數問合成器，不要自己猜

現在的 TTS（例如 Azure 的 SDK）可以在合成的時候回報「第幾句在第幾毫秒
開始」「每一個字在第幾毫秒」。拿得到就不要從波形猜。

**這件事對你特別重要**：參考片的切點是跟著旁白的語義走的，0.55 秒一次。
如果每一個切點都能吸附到某個字的時間，那整支片的節奏就是算出來的，
不是手排的。

---

## 三、參考片跟一般口播片最大的結構差別

一般的做法是**一句話一個畫面**：講完這一句，換下一個鏡頭。

參考片不是。它**一句話裡面可以換三四次畫面**。

這個差別會一路影響你的資料結構。如果你的模型寫出來的是

```
第 3 句：「紐約州有 62 個縣」
```

那你只能給它一個畫面。你要的其實是

```
第 3 句：「紐約州有 62 個縣」
   切點：A（州縣界圖）→ 0.4 秒後 → S（州單色輪廓）→ 0.6 秒後 → A
```

**所以請從一開始就設計成「一句話帶一串切點」。** 這是那種先做成一句一格、
之後再想辦法拆的東西 —— 一旦分頁邏輯建立在「一句＝一頁」上面，要改回來
會動到每一個地方。

至於那一串切點由誰決定：讓模型寫**代碼和語義**（「這裡要看到全州」），
秒數由旁白的字時間算。模型不擅長估秒數，但很擅長說「這句話在講哪個範圍」。

## 四、這種片子的錯，絕大多數不會報錯

這是我最想讓你先知道的一件事。

畫面的錯沒有 exception：標籤被推出畫面、地名疊在一起、紅圈圈到隔壁的州、
顏色兩個圖層撞色、字幕蓋住地圖的重點 —— 程式跑得完完全全成功，
exit code 0，只有人看的時候才存在。

所以**能畫出來比對的，就不要讀程式判斷**。例如：

- 挪一格看哪些像素變了 → 知道某個元素的實際外框在哪
- 同一個預設畫兩次逐像素比 → 確認它真的是可重現的
- 改了程式之後，拿改之前的版本畫同一格逐像素比 → 確認沒有動到不該動的

還有一種更貴的：**不是回報零，是回報一個看起來合理的替代品**。
地圖找不到某個縣的多邊形，退回去畫州的輪廓 —— 畫面上完全正常，
而它是錯的。回零還看得出不對，這種看不出來。

## 五、起手式：我會照這個順序做

**不要先設計整條管線。** 這種專案最容易在還沒確認「地圖畫得出來」之前，
就把流程、資料結構、prompt 全部寫好。

1. **產出一張圖。** 9:16、至少 1080×1920、指定的中心點和縮放、疊一個
   多邊形圖層並填色。在這一步卡住的話後面全部不用談。
   同時確認底圖的使用與標註授權（那份文件的實作順序第一條就寫了）。
2. **把那張圖的參數變成一個宣告。** 一個 JSON 一個預設，跑一次產出一張圖。
   做到 3 到 5 個預設就停，先不要做滿 14 個。
3. **手寫一份分鏡**（第幾秒切到哪個代碼），用程式壓成一支無聲的片。
   這時候還沒有模型、沒有旁白。
4. **逐格比對壓出來的片跟分鏡一致。** 不要用眼睛掃過去。
5. **加旁白，讓切點吸附到字的時間。** 這一步之後片子才算活的。
6. **最後才讓模型寫分鏡。** 而且它寫的是代碼和語義，不是秒數。

第 3 步和第 4 步很容易被跳過，因為「手寫分鏡」看起來像浪費時間。
但它是你唯一一次可以在沒有模型干擾的情況下，確認壓片這條路是對的。

## 六、跟模型要東西的時候

四條，都是量出來的，跟題材無關。

**一、算得通的數字才擋得住。** 給一個模型自己一算就發現不合理的數字，
它會在回覆裡明講「我不照它」然後用自己估的。**把算式攤開寫進 prompt**
（總共幾秒、其中多少是停頓、真正講話幾秒、每秒幾個字、乘起來就是上限），
它就照做。

**二、下限和上限是兩道門。** 只給上限，它會寫在下限附近；只給下限，
它會剛好踩在下限上。要多少就把下限訂在多少。

**三、規則裡每一條退路都會被走到。** 寫了「做不到就照抄上面那一句」，
它就會去抄。不想要的退路不要寫。

**四、不要給一個格式正確的範例答案。** 範例會被原封不動抄回來當答案。

還有一條是判斷不是量測：**想讓模型照某個風格寫，加檢查沒有用** ——
檢查只會讓它重擲一次。要找程式能直接控制的那一層（版面的算式、
合成器的參數、預設的清單）。

## 七、地理這個題材我還沒有答案的

這幾個我沒有證據，你要自己試：

- **14 個預設是不是夠？** 那是一支講紐約的片。講一個國家、一條河、
  一場戰役，需要的預設可能完全不同。有沒有一組「通用的鏡位語彙」
  （洲級／國級／省級／市級／地標），還是每個題目要重做一批？
- **地名標籤怎麼跟著地圖走。** 那份文件說標籤的定位錨點必須跟著地圖移動，
  但沒說怎麼做。這大概是最容易做到「看起來對、其實飄掉」的一塊。
- **0.55 秒一格會不會太快。** 那是參考頻道的節奏，不一定是你要的。
  這個數字值得自己驗，而且只有看片的人能判。
- **資料從哪裡來。** 行政區多邊形、海域邊界、縣界 —— 這些是有版權和
  精度差異的資料集，選哪一份會決定畫面長什麼樣。
