# 唸起來通不通順，是這幾件事決定的

**這一份很重要。** 成片的好壞，觀眾第一秒感覺到的是「唸起來順不順」，
而那完全由這裡的幾個決定造成 —— 跟文案寫得多好無關：同一份稿子，
用錯的方式唸出來就是不通順，而且**每一道門都會過**，因為沒有一個欄位
叫「順不順」。

這一份把散在 `core/voice.py`、`core/narration.py`、`docs/AUK.md` 和
commit `340b91e` 裡的心得收在一起。**全部是量出來的**，不是想出來的。

---

## 一、整篇一次唸完，不要一句一個檔

最早是一句配一個音檔，再接起來。**分開生成的代價量得出來**：

```
                    開頭偏高      散開
十一句 AuK 逐句      +4.48 半音    1.29
                    ↑ 十一次一模一樣地「重新起音」

                    結尾偏低      散開
十一句 AuK 逐句      −4.11 半音    1.61
接成一批三句         −1.64 半音    2.96
```

**語調跨不過句子的邊界，因為根本沒有邊界可以跨。** 一句一個檔的時候，
模型每次都從零開始決定這一句的音高和語氣，於是十一句像十一個人各唸一遍。

Azure 上同一份定稿量下來：

```
            一句一個    一次唸完
語速變化      0.23        0.34
句尾下收     -4.71       -6.71
```

所以**最終的做法是：整篇一次唸完，產出一條音軌，從頭到尾不切開。**

每一句在音軌上的位置怎麼知道？合成的時候在每一句前面插一個
`<bookmark mark="L7"/>`，Azure 會回報它在第幾秒經過那個標記。書籤本身
不發聲，所以它不影響唸法。

```
core/voice.py   whole_reading()   回整條音軌 ＋ 每句的起訖
                _warm_azure()     照書籤切回一句一個檔 ← **舊的壓法**
core/flow.py                      整條鋪在成片上      ← 2026-09-23 之後
```

**「切回一句一個檔」是舊的壓法，不要照它做。** 新的壓法是整條鋪上去，
畫面照書籤回報的秒數去對。

## 二、句子之間不要補任何標點

```
core/voice.py   JOIN = ""
```

接起來唸的時候，句與句之間**什麼都不加**。中文句子本來就自帶句號，
多塞一個標點會讓合成器唸出多餘的停頓。

**這裡踩過一次：替每一行補句號。** 唸出來一直斷，因為一行不等於一句話
—— 一行可能是兩個短句連著講，補了句號就變成兩句各自收尾。而且一個句號
在 Azure 是 0.425 秒，26 行就是 11 秒憑空多出來的空白。

---

## 三、句號後面停多久，程式決定

```
narration.sentence_gap_ms      預設 150（Azure 自己的預設是 630）
```

模型寫幾個句號每次不一樣 —— 11 句 11 個句號，用 Azure 預設就是 **6.9 秒
的空白，沒有人控制**。

這一格量過：

```
從預設調到 150     四個句號省 1.18 秒     ← 有效
從 150 調到 0      四個句號只省 0.34 秒   ← 已經調到底了
```

而且**它只動空白**：實測三種值之下，音高中位數、音域一模一樣，去掉靜音
之後長度也一樣。所以它治得了「總共停多久」，治不了「停在哪裡」。

---

## 四、停在哪裡、哪幾個字要慢，就地標在字裡面

這是整套裡最關鍵的一件，也是最容易搬漏的一件。

```
⏸0.3          停頓。插在任何位置，包括句子中間
⟪-10 第三次⟫   變速。包住要變速的那幾個字，不必整句
```

```
英國空管的官方說法，就四個字，⏸0.3技術問題。
同一套系統，三年內壞了⟪-10 第三次⟫。
```

**為什麼是就地標記，不是另開一欄。** 這個專案為「另開一欄，程式拿去找」
修過一次 —— 封面的強調字本來是把要變色的字另外列一欄，程式去正文裡找，
結果**找不到、找到兩次、跨行都不報錯**。改成 `機場*沒有飛機*` 之後三種
錯一次消失，因為位置就在字裡面。

停頓和快慢是同一個形狀，而且更嚴重：它們要指的不是一整句，是
「這三個字」「這個逗號後面」。

**值只能從清單裡挑**（`assets/rules.json` 的 `narration.pauses` /
`narration.rates`），清單外的擋掉。給清單而不是範圍，是因為量過：
**範圍型的要求，模型會貼著極端寫。**

兩層相乘：整條的語速包在最外層，模型標的 `⟪⟫` 在裡面，所以「這幾個字
慢下來」是相對於整條的速度慢下來，不會被蓋掉。

## 五、整條的語速

```
narration.rate_percent      現在 +40%
```

量出來的：對照頻道整體 5.47 字／秒，我們 +0% 只有 4.0 —— 掃過之後 +40%
最接近。

## 六、秒數怎麼估

寫稿的時候要知道「這樣寫會唸幾秒」，那個公式是解出來的：

```
唸多久 ＝ 字數/8.22 ＋ 行數×0.50 ＋ 句號數×0.425 ＋ 宣告的停頓
```

怎麼解的：

```
整份稿子   41 行、54 個句號、564 字 → 開銷 43.5 秒
單獨測     1 行、4 個句號、28 字   → 開銷 2.2 秒
兩式解出   每行 0.50 秒　每個句號 0.425 秒
驗算       41×0.50 + 54×0.425 = 43.5 ✅
```

**句號比行更貴。** 第一版只有「每行 1.06 秒」，那是把兩件事混成一個數字
—— 一行寫三句比一行寫一句多付 0.85 秒，而那些秒數本來可以拿去講話。

但要小心：**這個公式是「發預算」用的，不是「量長度」用的**。畫面那一整
條路（分鏡、字幕、成片長度）用的全部是合成之後真的量到的秒數，一格都沒
有用估計值。估計值唯一的客戶是寫稿之前 —— 免得寫完才發現超長，而重寫一
次是七分鐘、一塊多美金。

## 這一套有哪些地方還沒搬齊

`geo/`（地圖短影音那條路）的狀況，2026-09-26：

```
有   整篇一次唸完、一條音軌、bookmark、壓片直接鋪整條
有   句號停多久、整條語速（但數字寫在 story.json，不是 rules.json）
有   多角色：同一份 SSML 裡多個 <voice> 區塊 —— 這個比 core/ 還多

缺   ⏸0.3      句子中間完全沒有停頓工具，只能整行之間停
缺   ⟪-10 …⟫   沒有變速
```

**缺的正好是「表情」那一半。** 搬的時候只看得到程式在做什麼，看不到
為什麼這樣做 —— 這一份就是為了那件事寫的。
